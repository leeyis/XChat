# 对话内媒体展示与播放设计

- 日期：2026-10-05
- 状态：用户已评审通过原型，授权开始实现。
- 原型：`ui-ref/xchat-desktop-prototype.html?review=media`。
- 首版范围：浏览器／WebView 可解码的常见音频、视频及动图。不支持的编码保留文件操作，不引入转码或播放器依赖。

## 用户行为

音频显示播放条、文件名、时长和大小；视频显示画面、原生播放控件及文件信息。音视频由用户主动播放，支持暂停和拖动进度。同一时间只有一条音视频播放。离开会话、页面隐藏或窗口失去焦点时暂停，返回会话后保留本次运行中的播放位置，不自动恢复出声。WebView2 隐藏窗口时可能不改变 `document.hidden`，因此同时处理窗口 blur／focus。

GIF、动态 WebP 和 APNG 按原文件展示。进入可见区域后播放，可暂停和恢复；暂停画面与发送原文件分别处理。普通图片继续按原有方式展示。收件尚未接收或正在传输时显示文件状态，完成后才显示播放器；本地发件可预览原文件，同时保留发送进度和取消动作。取消、重试、文件删除、源文件移动、播放解码失败均保留现有文件操作。

原生播放控件随浏览器／系统呈现。文件后缀用于识别媒体类别，不代表当前平台必然支持内部编码。Web 保留下载，桌面保留另存为和系统打开，Android 使用已有系统打开入口（包括 fd Provider URI）。

## 架构与数据流

消息继续使用现有文件消息模型及传输协议，不做数据库迁移。前端复用 `fileKind`、本地文件可用状态和现有文件动作，在文件消息内部选择图片、音频、视频或文件卡片。

新增媒体来源接口返回 `{url, mime_type, file_name, file_size}`。前端将 URL 直接交给 `<audio>`／`<video>`／`<img>`，不用完整 Blob 或 Base64 读取大音视频。Tauri 使用 `get_workspace_media_source` 命令，Web 使用 `/api/media-source/:message_id`。

Rust 共享流式响应器处理 GET／HEAD 和单个 HTTP Range。无 Range 返回 200，合法范围返回 206，不可满足范围返回 416。响应提供正确的 MIME、长度、`Accept-Ranges` 和 `Content-Range`。每次请求独立定位文件，不能让并发请求共享读游标。

桌面及 Android 本地文件入口以消息 ID 查询数据库，并使用回环地址与本地 token 保护。Web 入口沿用接收文件下载目录和 Web 受管 outbox 的限制，不向局域网开放桌面任意发件源路径。Android 的 `content://`／`fd:` 在文件句柄解析处处理，不能直接对共享 `dup` 游标并发 seek。

粘贴或拖入的常见栅格图片附件暂存保留原始字节、真实 MIME 和正确扩展名。截图仍使用 PNG。动画附件不得经过 canvas 转换后再发送；SVG 等静态输入沿用原有 PNG 转换。

## 方案取舍

1. **完整 Blob／data URL**：改动较少，但首播等待和内存随文件大小增长，不适合大音视频。
2. **现有服务上的安全 URL＋共享 Range 响应器（采用）**：复用现有 Rust 服务，桌面、Web 和移动端共享流式行为；各平台保留自己的读取权限。
3. **桌面自定义协议＋Web HTTP**：可隔离桌面访问，但增加协议注册和平台差异；当前服务已有本地媒体保护机制，首版无须新增协议。

## 错误与资源管理

源文件丢失、权限失效或解码失败时显示可理解的状态，提供当前平台可用的下载、重新接收或系统打开动作。消息刷新及传输状态更新不能重建正在播放的元素。移出会话时暂停播放器，清理不再使用的事件、观察器和临时预览 URL。

## 验收

- 发件、收件及历史消息中的常见音视频可直接播放，动图保留动画。
- 音视频不自动出声；播放互斥、会话切换暂停、返回保留位置。
- 大视频按需读取，拖到未缓冲位置可继续播放；Range 和 HEAD 的响应长度正确。
- 接收完成前无播放器；失败、取消、重试和文件不存在时的文件动作仍可用。
- Web 无法读取桌面任意源路径；本地媒体拒绝错误 token 和非回环访问。
- Android 句柄不会因播放器并发读取破坏上传或其他媒体请求；无法解码时有文件操作。
- 前端测试及构建通过；Rust desktop、web 编译与相关测试通过；实际可用平台执行隔离数据冒烟。
