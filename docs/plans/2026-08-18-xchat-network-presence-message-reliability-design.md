# XChat 网络发现、在线状态与消息可靠性优化设计

日期：2026-08-18

状态：产品方向与 UI 原型已确认，工程方案待评审

关联原型：`ui-ref/xchat-desktop-prototype.html`

## 1. 结论摘要

本轮优化不把问题归因于文件传输，也不把 VPN 一概禁用。需要同时解决五个相互关联、但职责不同的问题：

1. 设备发现只负责找到新设备，不再用高频全网段地址遍历承担在线心跳。
2. 在线状态由单一状态机维护，所有界面和通知读取同一份带版本状态。
3. 消息状态严格由真实事件推进，不用定时器或界面轮询模拟“已送达”。
4. 离线消息先持久化到逐收件人 Outbox，再由统一工作器重试，应用重启后仍可继续。
5. 传输连接设置明确超时并逐步复用，消除每条消息重复建连和状态刷新等待。

当前 UDP 行为不属于会无限自我放大的经典二层“广播风暴”，但属于高频应用层 UDP 扇出和地址扫描：每 2 秒遍历 `192.168.0.255` 到 `192.168.255.255` 等约 260 个目标，同时又在每张网卡上发送受限广播和组播。遇到代理 TUN、`/1` 默认路由、异地组网或复杂虚拟网卡时，这些包可能被大量交给隧道、代理或驱动处理，存在干扰钉钉、腾讯会议和局域网稳定性的现实风险。

因此首要措施是停止连续网段扫描、限制发现接口和发送预算；是否已经造成用户观察到的全部异常，仍需通过改造前后的抓包与延迟指标验证，不能仅凭现象下最终因果结论。

## 2. 已确认的产品决策

- 物理 Wi-Fi、以太网默认参与设备发现。
- 已识别的异地组网 VPN 默认参与发现，用户可逐接口开关。
- 代理 TUN、WSL、Hyper-V、Docker 和其他虚拟网卡默认排除，但允许用户明确开启。
- 主动发现只发送到用户勾选的接口，不沿默认路由遍历地址段，不再扫描 256 个 `192.168.x.255` 地址。
- VPN 不支持广播或组播时，使用固定设备地址或域名进行单播发现和连接。
- 这里的接口设置只控制发现和在线探测；实际消息连接仍遵循系统路由。目标网段由 VPN 接管时，消息自然走 VPN。
- 上线/下线提醒提供“智能提醒（默认）”“全部提醒”“关闭提醒”三档。
- 默认不为普通上线事件弹 Toast；短暂断线和自动恢复也不打扰用户。
- 消息状态采用“发送中、已发出、已送达、已读、等待对方上线、发送失败”的真实语义。
- 文件传输不设置额外速率上限；最大并行通道使用下拉框，支持 4（默认）、8、16。

## 3. 当前实现基线

### 3.1 已有的可靠性基础

当前代码已经具备一部分可复用能力，不需要推倒重来：

- `messages.client_message_id` 是稳定消息 ID，并有唯一索引，可用于幂等去重。
- `message_receipts` 已按消息和收件人保存 `delivered_at`、`read_at` 及回执补发状态。
- `DeliveryAck` 和 `ReadAck` 已纳入协议，单批最多 128 条。
- 接收端在消息落库后才记录本地送达并尝试回送 DeliveryAck，因此“已送达”已有正确的持久化基础。
- `resend_for_peer` 能补发未送达消息、回执和撤回，并按 `client_message_id` 保持幂等。
- SQLite 状态更新已防止 `read → delivered → sent → pending` 等倒退。
- 离线队列和回执均可跨应用重启保留。

这些能力应保留并统一到一条新链路，而不是再增加第三套消息队列。

### 3.2 发现流量现状

`src-tauri/src/network/discovery.rs` 当前行为：

- 每 2 秒构造一次 ONLINE 公告。
- 每张可用网卡分别发送 `255.255.255.255` 和 `224.0.0.167`。
- 同一周期再通过未绑定接口的 socket 向约 260 个目标发送，包括 256 个 `192.168.x.255` 地址。
- 每 30 秒重扫网卡。
- 每个收到的非 reply 公告都会单播回复。
- 固定设备地址或域名也在每个 2 秒周期收到一次单播公告。

单机基础尝试量约为 `260 / 2 = 130` 个 UDP 发送/秒，尚未计入逐网卡发送、固定地址、接收回复和多设备重复流量。包体不大，但系统调用、路由查找、TUN 捕获、代理规则匹配和回复放大都可能成为问题。

### 3.3 在线状态现状

- 发现公告同时充当心跳，`last_seen` 使用 Unix 秒时间。
- 10 秒未见公告判为离线，后台每 2 秒扫描一次，因此最坏约 12 秒才翻转。
- `get_all_peers()` 是读取接口，却会顺带执行离线翻转并丢弃返回的状态变化。
- 消息发送失败调用 `force_mark_offline()`，但该路径没有统一持久化，也没有统一发出 `peer-offline` 事件。
- 后台看门狗只通知“由自己刚刚翻转”的设备；如果状态先被 getter 或发送失败路径改掉，看门狗可能再也拿不到这次转换。
- 前端列表、聊天头部、右侧详情、通知和发送判断可能在不同刷新时刻读取到不同状态。

这解释了“对方已经下线却仍显示在线”“状态变化了但没有下线提示”以及多个区域显示不一致。

### 3.4 发送与回执延迟现状

- 前端先插入 `pending` 乐观消息。
- 后端将单聊消息落为 `pending` 后，在后台任务中新建 WebSocket 连接发送。
- 后台写入成功后只更新 SQLite 为 `sent`，没有立即发布专用的消息状态事件。
- 无其他事件时，前端依赖空闲状态下 5 秒一次的工作区轮询看到 `sent`。
- 对端落库后会发送 DeliveryAck，但该回执又需要新建一次反向 WebSocket 连接。
- `connect_async` 没有明确的短连接超时，遇到陈旧 IP、断开的 VPN 路由或黑洞路由时，系统连接超时会让“发送中”停留很久。
- 旧链路上线补发前固定等待 500 ms，并在文本消息之间等待 100 ms；新旧补发函数又会在同一次上线时各执行一次。

因此“窗口打开且对方在线，仍先显示几秒发送中”主要不是渲染慢，而是后台发送、重复建连和 5 秒轮询共同造成的可见延迟。

### 3.5 通知现状

前端收到 `peer.online` 和 `peer.offline` 后会无条件加入应用内 Toast；只要系统通知总开关开启，还会继续发送系统通知。当前没有：

- 智能/全部/关闭三档策略。
- 上下线去抖与短时重复合并。
- 当前会话、待发送消息等相关性判断。
- “正在确认连接”和“连接已恢复”的会话内状态。

## 4. 目标架构

```mermaid
flowchart LR
    A[接口清单与用户选择] --> B[DiscoveryService\n低频发现新设备]
    B --> C[PresenceService\n唯一在线状态机]
    D[单播 Probe/Pong\n或长连接 Ping/Pong] --> C
    E[TransportManager\n连接、超时、复用] --> C
    C --> F[OutboxWorker\n逐收件人补发]
    F --> E
    E --> G[接收端持久化]
    G --> H[DeliveryAck / ReadAck]
    H --> I[MessageStateService\n单调状态推进]
    C --> J[统一 Presence 事件]
    I --> K[统一 Message 状态事件]
    J --> L[列表、头部、详情、横幅、通知]
    K --> L
```

职责边界：

- `DiscoveryService`：寻找未知设备和更新地址，不决定通知文案。
- `PresenceService`：融合发现、探测、传输成功/失败和主动退出信号，唯一有权改变在线状态。
- `TransportManager`：建立或复用连接，执行连接/写入超时，反馈可验证的传输结果。
- `OutboxWorker`：读取持久队列并按收件人顺序发送，不依赖当前界面是否打开。
- `MessageStateService`：校验状态只能单调前进，并向前端发布精确变更。
- 前端：只渲染后端事实和执行通知策略，不自行推断在线状态或用计时器升级回执。

## 5. 设备发现与广播控制

### 5.1 接口分类

新增稳定的网络接口标识，不用当前 IP 作为配置主键。建议保存：

- 系统接口 ID/LUID 或平台可提供的稳定标识。
- 当前名称、IPv4、前缀长度、接口类型、up/down 状态。
- 分类：`physical_lan`、`mesh_vpn`、`proxy_tun`、`virtual_machine`、`unknown`。
- 用户显式选择和最后一次可用时间。

顶层类别开关是总开关。关闭某类别时，其下接口开关禁用但保留原选择；接口恢复或 IP 变化后仍能恢复用户偏好。

### 5.2 发送范围

每张已启用接口只允许以下目标：

1. 该接口的 IPv4 定向广播地址，由 IPv4 与前缀长度计算。
2. 链路本地组播 `224.0.0.167`，显式设置 `IP_MULTICAST_IF`，TTL 固定为 1。
3. 用户配置的固定设备地址或域名，使用单播。

必须删除：

- `192.168.0.255` 到 `192.168.255.255` 的连续遍历。
- 未绑定接口 socket 对 `255.255.255.255` 的兜底发送。
- 依赖默认路由命中哪个网卡的发现逻辑。

如果平台暂时无法取得前缀长度，只发送该接口上的组播，不退回全网段扫描。Android 等受限平台可保留受限广播作为平台专用兼容路径，但必须单独设定低频预算，不能影响桌面端。

### 5.3 发送节奏

推荐默认值：

| 场景 | 节奏 | 目的 |
|---|---:|---|
| 应用启动 | 0 ms、400 ms、1500 ms，共三次 | 快速发现，抵抗单包丢失 |
| 接口变为可用 | 同启动突发 | 快速适配 Wi-Fi/VPN 切换 |
| 稳态发现 | 30 秒一次，增加 ±20% 抖动 | 发现后来启动的新设备，避免同频同步 |
| 固定地址发现 | 启动/网络变化立即一次，失败按退避重试 | 支持不转发广播的组网 VPN |
| 主动刷新 | 用户操作触发一次三包突发 | 可解释、可控的手动恢复 |

发现包不再作为高频在线心跳。每个 `(peer_id, sequence, interface_id)` 在短窗口内去重，reply 每个 sequence 最多回复一次，避免同一公告从广播和组播双路径到达时重复回复。

### 5.4 VPN 与代理 TUN

- WireGuard、Tailscale、ZeroTier 等组网接口只有被识别或用户选择后才参与主动发现。
- 组网 VPN 不转发广播/组播时，引导使用固定地址/DNS；已保存设备继续按系统路由通信。
- Mihomo/Clash 等代理 TUN 默认不参与发现。用户强制开启时显示风险确认。
- 发现发送必须绑定到目标接口；不能因系统存在 `0.0.0.0/1`、`128.0.0.0/1` 等代理路由而把地址扫描交给 TUN。
- 设置页的“刷新网络列表”只刷新接口清单，不立即发起无界扫描。

## 6. 在线状态与心跳

### 6.1 状态模型

后端使用四态，前端不得另外维护一套布尔值：

| 状态 | 含义 | UI |
|---|---|---|
| `unknown` | 历史设备，启动后尚未得到本轮证据 | 显示“状态未知”，不弹提醒 |
| `online` | 最近收到有效公告、ProbeAck、Pong 或成功业务响应 | 在线 |
| `suspect` | 连续丢失探测或一次连接异常，正在确认 | “正在确认连接…” |
| `offline` | 达到确认阈值、收到 Goodbye，或硬失败后复核失败 | 离线 |

状态记录至少包含：

- `peer_id`
- `state`
- `generation`：每次状态转换递增
- `last_seen_monotonic`
- `last_seen_wall_clock`：仅用于展示和持久化
- `last_transport_ok_at`
- `failure_streak`
- `reason`
- `active_interface_id`

进程内超时计算使用单调时钟，避免系统校时造成误判；Unix 时间只负责展示和重启恢复。

### 6.2 探测策略

对已知设备使用单播探测或长连接 Ping/Pong，不再通过全网广播确认在线：

- 当前会话、存在待发送消息或活跃传输：每 2 秒探测一次。
- 其他已知在线设备：每 5 秒探测一次。
- 连续两次未响应进入 `suspect`。
- 活跃设备连续三次未响应，目标 6 秒内确认离线。
- 空闲设备连续三次未响应，目标 15 秒内确认离线。
- `ConnectionRefused` 等硬失败可立即进入 `suspect`，再执行一次快速单播复核；单次超时不能直接判离线。
- 成功的消息响应、DeliveryAck、ReadAck、ProbeAck 或 Pong 都可立即恢复 `online`。
- 正常退出发送 best-effort `Goodbye`，接收端可立即离线；不能把 Goodbye 当作唯一依据。

上述周期应加入小幅随机抖动，避免多台设备在同一时刻集中探测。

### 6.3 单一转换入口

禁止以下行为：

- getter 在读取时修改在线状态。
- 发送函数直接修改 `Peer.is_offline`。
- 前端根据一次 API 失败自行显示离线。

所有输入都提交给 `PresenceService`，由它串行执行：

1. 验证证据与当前 generation。
2. 计算下一状态。
3. 持久化状态、原因和时间。
4. 更新内存快照。
5. 发布一个带 generation 的 `presence.changed` 事件。

列表、聊天头部、右侧设备详情、发送决策和连接横幅都从同一个快照派生。前端仅接受 generation 更大的事件，避免旧轮询覆盖新状态。

## 7. 消息状态语义

### 7.1 用户可见状态

| 状态 | 严格语义 | 触发条件 |
|---|---|---|
| `发送中` | 本机正在持久化或进行本轮网络提交 | UI 发起后到 Outbox 入库/本轮写入完成，通常应低于 300 ms |
| `已发出` | 消息已离开本机，正在等待对端确认 | 连接上的完整帧写入成功；不代表对端已持久化 |
| `已送达` | 对端已验证并持久化消息 | 收到明确 DeliveryAck |
| `已读` | 对端明确报告已读 | 收到 ReadAck；不能用窗口在线或时间推测 |
| `等待对方上线` | 已可靠保存在本机 Outbox，当前不适合继续快速重试 | Presence 为 offline，或可重试的连接失败已转队列 |
| `发送失败` | 本地数据错误、权限错误、协议不兼容等不可自动恢复问题，或用户明确停止重试 | 终止错误；普通断网不显示为失败 |

“已发出”在中文界面取代当前容易被理解为送达的“已发送”。生产数据可继续内部使用 `sent`，仅调整展示名称。

### 7.2 状态推进规则

单聊主状态：

```text
sending -> queued(waiting_peer) -> sent -> delivered -> read
    |              ^                |
    +-> sent ------+                +-> queued（禁止）
    +-> failed_terminal
```

约束：

- `sent`、`delivered`、`read` 单调前进，永不因重试或旧快照倒退。
- `sending` 是短暂本地状态，不应跨应用重启长期保留；重启后未完成项恢复为 `queued`。
- 网络异常把消息转为可重试 `queued/waiting_peer`，不是终止失败。
- 同一 `client_message_id` 重复到达时返回已有结果，不重复展示、不重复系统通知。
- 群聊按 `message_receipts` 逐收件人维护；气泡展示“已送达 x/y · 已读 x/y”，不把部分送达伪装成全体送达。
- 前端不得按时间自动把 `sending` 改为 `sent` 或 `delivered`。

### 7.3 事件驱动更新

增加统一事件 `message.status.changed`：

```json
{
  "conversation_id": "direct:a:b",
  "client_message_id": "uuid",
  "status": "sent",
  "delivered_count": 0,
  "read_count": 0,
  "recipient_count": 1,
  "version": 3,
  "changed_at": 1787040000,
  "reason": "transport_write_ok"
}
```

所有数据库状态写入成功后立即发布事件，包括 `pending/queued -> sent`。前端按 version 合并，不再等待 5 秒工作区轮询。轮询仅作为断事件后的低频修复路径，不承担正常状态推进。

## 8. 离线 Outbox 与补发

### 8.1 数据模型

复用 `messages` 和 `message_receipts`，增加逐收件人的发送队列字段或独立 `message_outbox` 表。推荐独立表，避免把“用户可见回执”和“本机发送调度”混在同一行：

| 字段 | 作用 |
|---|---|
| `message_client_id` + `recipient_id` | 复合主键，保证逐收件人幂等 |
| `state` | `queued`、`in_flight`、`sent`、`failed_terminal` |
| `attempt_count` | 退避与诊断 |
| `next_attempt_at` | 下次可重试时间 |
| `lease_until` | 防止多个工作器重复并发发送 |
| `last_error_code` | 分类失败原因，不保存敏感正文 |
| `updated_at` | 恢复和观测 |

消息正文仍只保存在 `messages`；Outbox 不复制正文。

### 8.2 入队事务

发送动作在一个 SQLite 事务内完成：

1. 以 `client_message_id` 幂等写入消息。
2. 创建全部收件人的 receipt 占位行。
3. 创建全部收件人的 Outbox 行。
4. 提交事务。
5. 返回前端并触发工作器。

只有事务提交后，前端才认为消息已可靠保存在本机。即使应用随即崩溃，重启后也能继续补发。

### 8.3 工作器触发条件

- 新消息成功入队。
- Presence 转为 online。
- Transport 建立或恢复。
- 应用启动完成。
- 网络接口发生变化。
- 周期性安全扫描。

不再只依赖“离线 → 上线”边沿，因为任何一次事件丢失都不应让队列永久卡住。

### 8.4 重试策略

- 同一收件人按消息时间和数据库 ID 有序发送。
- 首轮立即尝试；失败后建议使用 1、3、10、30、60 秒退避，之后封顶 5 分钟，并增加 ±20% 抖动。
- Presence 已明确 offline 时停止快速重试，只等待状态恢复和低频安全扫描。
- 连接恢复后按小批次发送，避免同时为每条消息新建连接。
- DeliveryAck 和 ReadAck 自己也是持久待办，独立重试；不能因为原消息已显示而丢失回执。
- 传输采用至少一次投递，接收端依靠 `client_message_id` 实现用户体验上的恰好一次。
- 切换会话、窗口关闭或前端刷新不得影响队列。

旧的 `resend_pending_messages` 与新的 `resend_for_peer` 应迁移为同一 OutboxWorker，完成兼容数据迁移后移除固定 500 ms 握手等待和每条消息 100 ms sleep。

## 9. 连接与延迟优化

### 9.1 第一阶段：明确超时与即时事件

在不改变协议的前提下先完成：

- TCP/WebSocket 连接超时：局域网建议 800 ms，VPN 建议 1500 ms；可按接口类型选择。
- 单次消息总提交超时建议 2 秒，超时后进入 Outbox，不继续让 UI 停在“发送中”。
- 写入成功立即发布 `sent` 事件。
- 收到回执立即发布 `delivered/read` 事件。
- 陈旧地址失败后，从 PresenceService 获取最新地址只快速重试一次，避免旧 IP 与新 IP 双重长等待。
- 新协议路径不再先 WS 失败、再无限等待 TCP fallback；兼容 fallback 也必须共享总超时预算。

### 9.2 第二阶段：每设备连接复用

增加 `TransportManager`，每个设备维护至多一条可用的消息会话：

- 首条消息建立连接，后续消息、Probe、回执和控制消息复用。
- 使用有界发送队列，防止慢设备拖垮全局。
- 连接空闲后延迟关闭，不为每个回执重复握手。
- Ping/Pong 结果输入 PresenceService。
- 双方同时建连时按稳定 peer ID 决定保留哪一条，避免双连接抖动。
- 连接断开只影响对应 peer，不阻塞其他设备。

连接复用完成后，健康局域网中的“发送中”应接近不可感知；“已送达”的主要耗时只剩一次消息传输、对端 SQLite 提交和回执返回。

## 10. 上下线提醒与连接横幅

### 10.1 默认智能提醒

“智能提醒”执行以下规则：

- 普通上线不弹 Toast、不发系统通知。
- `online -> suspect -> online` 的短暂波动不弹 Toast。
- 只有确认离线且满足至少一项相关性条件时提醒：当前打开该会话、存在待发送消息、存在活跃传输或用户正在查看该设备。
- 同一设备短时间反复变化合并为一次事件。
- 当前会话进入 suspect 时显示“正在确认连接…”，确认离线后持续显示“对方当前离线”。
- 恢复后显示“连接已恢复”；有队列时显示“连接已恢复，N 条待发送消息正在自动补发”，随后自动收起。

### 10.2 全部提醒与关闭

- “全部提醒”：只对已经确认的 online/offline 转换提醒；5 秒内重复事件合并，仍不展示 suspect 中间态 Toast。
- “关闭提醒”：不显示上下线 Toast 和系统通知，但列表、聊天头部、详情及连接横幅仍更新。
- 新消息通知开关与上下线提醒策略分离，关闭上下线提醒不能关闭消息通知。

### 10.3 一致性要求

一个 `presence.changed` 事件必须原子更新：

- 会话列表状态点。
- 聊天头部状态。
- 右侧设备详情。
- 发送逻辑。
- 连接横幅。
- 通知策略输入。

不允许出现“横幅已恢复、头部在线、详情仍离线”的跨区域状态撕裂。

## 11. 文件传输并行通道

文件传输与本轮广播异常分开处理，不把文件上传视为当前网络不稳定的前提原因。

- 设置项名称为“最大并行通道”，不是“线程数”。
- 下拉选项为 4（默认）、8、16。
- XChat 不设置额外速率上限；所有文件传输共享全局并行上限。
- 实际通道数取本机设置、对端能力与任务条件的安全最小值。
- 设置保存后只影响新开始的传输，已有传输不中途重组。
- 旧版设备或未声明 `parallel_file_v2` 能力时回退到 4。
- 16 通道会增加 CPU、内存、磁盘随机 I/O 和 socket 数量，UI 已明确提示。
- 工作器必须公平分配通道，单个大文件不能长期占满全局资源。

## 12. 可观测性与诊断

没有指标就无法证明腾讯会议、钉钉异常是否由 XChat 引起。至少增加以下结构化指标和日志：

### 12.1 发现

- 每接口每分钟公告尝试、成功、失败数量。
- 每目标类型：广播、组播、固定单播。
- 接收公告数、去重数、reply 数。
- 被排除接口和排除原因。
- 当前发现发送预算。

### 12.2 Presence

- 状态转换、generation、reason、持续时间。
- Probe RTT、连续丢失次数。
- 从最后成功证据到 offline 的耗时。
- suspect 后恢复次数，用于评估误判率。

### 12.3 消息

- `client_submit -> persisted -> sent -> delivered -> read` 各阶段延迟。
- 建连耗时、写入耗时、回执 RTT。
- Outbox 深度、最老消息年龄、尝试次数和错误分类。
- 幂等重复命中数。

日志不得记录消息正文、完整文件路径或敏感 VPN 凭证。设备 ID 可在诊断导出时做截断或哈希。

## 13. 协议与兼容

- 当前发现协议版本为 2；新增 Probe/ProbeAck/Goodbye 时把发现协议升级为 3，并通过 capability `presence_probe_v1` 协商。
- v3 节点继续解析旧 `LANChat|ONLINE` 公告，但不恢复全网段扫描。
- 新增的 Probe、ProbeAck、Goodbye 和状态序号必须有大小限制、版本字段和发送者 ID 校验。
- 未支持 `presence_probe_v1` 的设备继续通过低频发现公告更新在线状态，界面可使用更保守的超时，不影响消息互发。
- 已有 `DeliveryAck`、`ReadAck` 和 `client_message_id` 序列化字段保持兼容。
- SQLite 迁移延续现有窄迁移方式，不要求用户清库。
- Desktop 与 Web 共用 Rust 核心中的 Presence、Outbox 和状态推进逻辑，不能在两个入口各实现一份。

## 14. 分阶段实施

### 阶段 A：诊断与发现流量止血

1. 为现有发现发送增加计数和接口日志。
2. 实现接口分类与已选择接口配置读取。
3. 删除 256 地址扫描和默认路由兜底。
4. 落实启动突发、30 秒稳态发现、去重与发送预算。
5. 固定地址改为带退避的单播发现。

这是最高优先级，应先验证钉钉和腾讯会议受影响的问题是否消失。

### 阶段 B：统一 Presence 状态机

1. 把 `PeerManager` 的状态修改迁入 `PresenceService`。
2. 让所有 getter 成为纯读取。
3. 增加 unknown/suspect/online/offline、generation 和 reason。
4. 发送失败只提交证据，不直接改布尔值。
5. 原子持久化并发布 `presence.changed`。
6. 落实智能/全部/关闭提醒和连接横幅。

### 阶段 C：消息状态即时化

1. 固化状态语义和单调规则。
2. 每次数据库状态变化发布 `message.status.changed`。
3. 前端按 version 合并并移除正常路径上的 5 秒等待。
4. 为连接与发送设置总超时预算。
5. 校正离线时的“等待对方上线”显示。

### 阶段 D：统一 Outbox

1. 建立逐收件人 Outbox 迁移。
2. 合并两套补发路径。
3. 增加租约、退避、启动恢复和周期安全扫描。
4. 把消息、回执、撤回和群消息都接入统一调度。
5. 验证崩溃恢复、重复投递和顺序性。

### 阶段 E：连接复用与文件并行配置

1. 实现每设备 TransportManager。
2. 复用消息、回执、控制消息与心跳连接。
3. 接入 4/8/16 全局文件并行通道设置。
4. 完成性能基准和多设备压力验证。

每个阶段可独立上线和回滚，禁止将所有网络、状态和文件改造堆进一次不可诊断的大提交。

## 16. 验证方案

### 16.1 自动测试

- 接口分类、默认排除和用户覆盖。
- 指定接口的广播地址计算；任何测试都不得生成 256 地址列表。
- Presence 状态机的丢包、恢复、Goodbye、硬失败和旧 generation 事件。
- getter 不修改状态。
- `sent -> pending`、`delivered -> sent`、`read -> delivered` 均被拒绝。
- Outbox 入队事务、租约过期、退避、重启恢复和逐收件人顺序。
- 重复消息、重复 DeliveryAck、乱序 ReadAck 幂等。
- 回执发送失败后重启仍可补发。
- 智能提醒不提示普通上线和短暂抖动，只提示相关的持续离线。

### 16.2 网络集成测试

- 两台物理局域网设备互相发现和消息互发。
- WireGuard 异地组网自动发现；不支持广播时固定地址成功连接。
- Mihomo/代理 TUN 开启但未勾选时，抓包确认 XChat 发现流量为零。
- VPN 断开、恢复、IP 变化后地址和 Presence 原子更新。
- 丢弃 1、2、3 次 Probe，验证 suspect/offline 阈值。
- 黑洞路由、ConnectionRefused 和过期地址不会让“发送中”无限停留。
- 发送端/接收端在入队、写入、落库、回执各阶段崩溃后恢复。
- 10 台和 50 台设备并存时无同步突发和 reply 放大。

### 16.3 用户场景验收指标

| 指标 | 目标 |
|---|---:|
| 启动后发现同网段新设备 | 通常 ≤ 2 秒 |
| 健康局域网“发送中”停留 | P95 ≤ 300 ms |
| 健康局域网送达回执 | P95 ≤ 800 ms |
| 正常 VPN 送达回执 | P95 ≤ 2 秒 |
| 活跃设备确认离线 | ≤ 6 秒 |
| 空闲设备确认离线 | ≤ 15 秒 |
| 状态恢复后界面一致更新 | ≤ 500 ms |
| 已确认离线后的消息入队显示 | ≤ 300 ms |
| 排除接口上的发现包 | 0 |
| 桌面稳态地址扫描包 | 0 |

延迟目标需要在可控局域网和实际 VPN 环境分别测量；网络本身丢包或高 RTT 时记录环境，不把不可控链路延迟归咎于 UI。

### 16.4 对其他应用的影响验证

在同一台 Windows 设备、同一网络和相同 VPN 配置下做 A/B：

1. XChat 未运行。
2. 当前版本 XChat 运行。
3. 完成阶段 A 的 XChat 运行。

同时记录 XChat 每接口包数、系统网络吞吐、丢包、网关 RTT、腾讯会议音视频延迟，以及钉钉图片/文件发送成功率。阶段 A 相比未运行基线不应产生可感知的会议延迟或文件发送失败；若仍异常，再继续排查端口冲突、驱动、CPU、磁盘和其他系统因素。

## 17. 完成标准

- 桌面端不再执行连续网段广播地址扫描。
- 代理 TUN 和虚拟网卡默认无发现流量，用户选择的组网 VPN 仍可通信。
- 在线状态只有一个写入者，所有界面区域在同一 generation 下保持一致。
- 普通上线和短暂抖动不再反复弹窗。
- 健康在线设备的消息状态不依赖 5 秒轮询。
- “已发出、已送达、已读”分别由写入成功、DeliveryAck、ReadAck 推进。
- 离线消息、回执和撤回在应用重启后仍可自动补发，重复投递不重复展示。
- 文件并行通道可选择 4、8、16，默认 4，并与发现流量问题解耦。
- Desktop 和 Web 的共享逻辑测试通过，并在真实局域网、WireGuard 和代理 TUN 场景完成抓包验收。
