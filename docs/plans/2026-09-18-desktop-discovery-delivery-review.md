# 桌面设备地址刷新与消息可靠性：分析及原型评审

日期：2026-09-18。阶段：第一步，原型与修复方案。尚未实施本轮生产代码修改。

原型：[ui-ref/xchat-desktop-prototype.html](../../ui-ref/xchat-desktop-prototype.html)。直接用浏览器打开，无需构建或联网。保留既有移动端 `#mobile-review` 入口。

本次结论来自当前工作区源码，工作区已经包含其他未提交修改。没有受影响双机的运行日志、数据库样本和客户端版本，因此下文确认的是代码行为及缺口，不能认定每一项都已经在用户那台客户端上发生。

## 1. 本次原型

- 聊天顶部增加「刷新地址」，设备详情增加「刷新设备地址」。点击后展示发现候选地址、核对设备 ID、验证消息连接、更新地址的过程。
- 「设备」列表提供「重新发现」，面向所有设备重新执行发现与验证；不是仅刷新本地列表。
- 初始示例中张三仍保存 `192.168.1.42:8888`，刷新成功后切换为 `192.168.1.86:8888`。保留设备 ID、备注和聊天记录，显示旧地址与新地址。
- 收到广播显示「已发现 · 连接待验证」；验证成功才显示「在线 · 连接已验证」。发现状态与消息通道可用性分开表达。
- 找不到设备、设备 ID 不匹配均保留历史地址，不虚构新地址，不自动合并到其他设备。
- 单聊示例区分「发送中」「已发出 · 等待回执」「已送达」「未确认送达」。超时不等于确定未送达，提示对方可能已收到；「重新发送」操作复用同一条消息。
- 文件卡片移除常驻「打开」及下拉按钮。右键菜单和悬浮「更多」菜单统一为：复制/转发/引用等原有操作之后，**打开文件 → 打开目录 → 另存为**，再到撤回/删除。
- 未接收或本地文件不可用时，打开文件、打开目录、另存为禁用。文件卡片支持 Shift+F10，菜单支持方向键与 Escape。
- 左侧底部是明确标注的原型场景控制：地址变化、未找到设备、身份不匹配、回执超时，以及一键查看文件菜单。网络、打开文件、打开目录均为模拟，不调用真实系统操作。

## 2. 已确认的代码行为

### A. 历史固定地址会压过最新发现地址，是地址问题的高优先级嫌疑

证据：

- `src-tauri/src/network/discovery.rs:1027`，`select_peer_endpoint`：只要设备 ID 在 `verified_endpoints` 中，就直接选固定地址，不选择当前 UDP 包的源 IP 加公告端口。
- `src-tauri/src/network/peer_identity.rs:85`，`verified_endpoints_by_device_id`：在固定地址记录之间按 `last_verified_at` 选最新，但没有验证时间过期或本次可达性判断。
- `src-tauri/src/db.rs:1614`，`CustomPeerRecord::is_verified`：仅检查设备 ID 非空。
- `src-tauri/src/peers.rs:40`，`reconcile_verified_peer_endpoints`：启动恢复时也用固定地址覆盖已保存的设备地址。

可推导出复现链：设备曾在 A 地址手工验证 → DHCP 变成 B → 收到 B 的上线广播 → 仍因固定记录选择 A → 上线提醒产生，但消息连向 A。重新手工添加 B 会刷新验证记录，使 B 被选中，因而与用户描述高度吻合。

这个结论有条件：必须存在该设备的固定地址绑定。没有固定绑定时，发现监听器会使用 UDP 源 IP；`PeerManager::add_or_update_with_details`（`peers.rs:127`）确实会覆盖 `peer.addr`，并不是全局「从不更新 IP」。

不能直接删除固定地址优先策略。它已有保护 NAT/端口映射场景的测试，UDP 观察地址不一定就是可连接的服务地址。应改成候选地址验证和有期限的偏好。

### B. 收到上线广播会直接判在线，但尚未证明消息服务可连接

`discovery.rs:1787` 的桌面监听器经过发现策略过滤后，调用 `add_or_update_with_details`，再触发 `peer-online` / `new-peer`。`peers.rs:151` 附近直接设置地址、更新时间和 `is_offline=false`。

其中没有对所选地址做消息 WebSocket 握手。UDP 能发现与 TCP/WebSocket 能发送是两条不同路径。多网卡、多子网或代理接口带来的多个公告，也可能轮流覆盖同一设备当前地址；当前 peer 模型没有候选集和本轮连接评分。这是代码支持的风险，是否命中现场需查看实际网卡和选址日志。

发送时已有 `open_verified_ws`（`messaging.rs:326`）核对目标设备 ID 的保护，应保留。它能阻止旧 IP 被另一台设备占用时错投，但不能帮助发送者主动找到最新地址。

### C. 「发出」仅证明写入连接，不能证明对方持久化

`messaging.rs:286` 的 `send_json_via_ws_expecting_reply` 写入帧后立即返回成功；回执由后台读取。`workspace.rs:1191` 随即把消息推进为 `sent`。

`messaging.rs:267` 的同连接回执窗口是 1,200 ms。窗口耗尽只结束读取，不会让之前返回的成功变成失败，也没有对应的显式「回执超时」结果。

接收端 `web_server.rs:2675`、`:2705` 附近对协议解析或稳定单聊处理失败主要记录日志。发送者可能已经写出，但对方未成功保存；目前无法凭写入结果报告「对方收到」。UI 应仅在 `DeliveryAck` 后显示已送达；超时只能标注未确认。

现有基础不应丢弃：接收端先保存稳定单聊消息（`web_server.rs:2564`），再记录送达及产生回执（`:2576`）；数据库还有状态单调推进（`db.rs:2495`）和 `client_message_id` 去重/冲突校验（`:2437`）。

### D. 首发与补发对回执连接的处理不一致

- 首发：`workspace::send_message` → `send_direct_message_expecting_reply`，保留连接读取一段时间。
- 补发：`workspace::resend_for_peer`（`:1520` 附近）→ `send_direct_message`（`messaging.rs:158`）→ `send_json_via_ws`（`:270`），写完立即 close。
- 接收端已经支持同连接回送（`web_server.rs:1992`、`:3260`），并保留反向回执补发作为兼容兜底。

所以当反向连接不可达时，首发与补发行为存在差异。补发可能已被对方保存，但回送未被本机消费，造成持续未确认及重复重试。这里只能认定可靠性缺口，不应把它直接写成「对方一定没收到」。

### E. 自动补发漏掉引用与公告，且与离线检测串行运行

- `workspace.rs:1475` 的补发循环直接跳过 `msg_type != "text"`；发送入口支持 `text | quote | announcement`。引用和公告虽可进入待送达数据，却不被该循环补发。
- 当前已经有定时兜底：`discovery.rs:2296` / `:2299`，每 15 次、每次基准 2 秒，遍历在线设备补发。不能把当前代码描述为「只在重新上线才补发」。
- 但这个扫描器逐设备 `await resend_for_peer`；单设备内部又逐条补发。断网、大量未确认消息会延长整轮耗时，因此 30 秒只是无阻塞时的近似间隔，还可能推迟下一次离线判定。
- 原选址没修好时，周期性重试仍会使用同一错误地址。

群聊另有语义问题：`initial_send_status`（`workspace.rs:1032`）在至少一个收件人在线时直接返回 `sent`，实际发送在后续后台任务。应改为逐收件人确认来汇总状态。

## 3. 第二步建议实施方案

### 3.1 地址刷新与自动恢复共用 Rust 核心

建立按稳定设备 ID 管理的候选地址集合，记录来源、观察时间、最后验证时间、失败次数；区分用户配置的固定地址和本次可用的活动连接地址。

1. 自动触发：收到同设备新地址、网络接口发生变化、发送连接失败、应用从休眠恢复。UI 刷新调用同一套流程。
2. 限流触发短发现窗口，复用现有发现计划与网卡选择；不扫描所有任意网段，也不绕过被用户关闭的接口。
3. 候选包括最新发现地址、历史活动地址和手工固定地址。固定地址保留偏好，但验证过期或连续失败后允许其他候选胜出；NAT 固定地址若验证成功可继续使用。
4. 对候选执行并发有界、超时有界的身份及消息通道握手。匹配预期设备 ID 后才采纳，UUID 核对延续现有模型；它不是新增密码学认证。
5. 成功后原子更新内存活动地址、数据库和前端快照，发送地址变更事件；不要把每次地址变动当作新设备上线通知。以地址版本/本轮序号避免迟到的旧探测覆盖新结果。
6. 地址更新成功唤醒待发队列。失败返回结构化原因：没有响应、身份不符、服务不可达、接口策略关闭等，保留历史地址。

初始建议值：单候选握手沿用当前 3 秒上界，整轮刷新约 5–8 秒、最多 3 个候选并发；重复点击复用在途任务。具体数值在局域网与 VPN 双机回归后调整，不承诺跨隔离网段必然找到设备。

拟增加共享入口 `refresh_peer_connection(peer_id)` 和 `rediscover_peers()`；返回设备 ID、刷新结果、活动地址、原地址、验证时间、失败原因。桌面 Tauri 与 web API 只作适配。新增 Tauri 命令须同步 `main.rs`、`lib.rs`、`permissions/commands.toml` 和适用 capability。

### 3.2 消息发送采用持久队列与明确回执

- 复用现有 `messages`、`message_receipts` 与客户端消息 ID，避免另起重复消息系统。需要持久化重试时间/次数时添加兼容的字段或附属表，实施前确定迁移。
- 状态：本地保存/等待连接 → 正在发送 → 已发出等待回执 → 对方落库确认的已送达 → 显式已读。回执超时作为重试状态/诊断字段表达，不把已送达、已读降级。
- 首发、手工重试、定时补发统一发送路径，同连接读取回执；回执关联消息 ID、会话和收件人，接收端事务完成后确认。可协商的 NACK 返回明确拒收原因；旧版本不支持时保持未确认状态。
- 同一收件人和消息只保留一个在途重试，按退避与抖动调度；例如 1 / 2 / 5 / 10 / 30 秒，之后低频重试。网络恢复/地址验证成功可提前唤醒，避免重连时同时发送大量历史消息。
- 扩展补发到实际支持的 `text`、`quote`、`announcement`，保留类型、提及信息和原消息身份。文件仍复用独立传输状态机，不把完整文件当文本重试。
- 群聊按收件人维度保存发送与确认状态，只重试未确认成员；群同步失败应有清晰依赖结果。
- 将离线监测从网络重试中分离：扫描只判定和发事件，专门后台调度器负责有界并发投递，避免一个慢设备拖住所有设备。
- 保留现有按 ID 去重和单调状态保护。目标是可重试并去重，不承诺网络上的严格 exactly-once。

### 3.3 文件菜单实现

桌面实际前端已在 `frontend/src/App.jsx`、`frontend/src/xchat.js`，与根 AGENTS 中早期 `src/js` 映射不同。实施时以当前源码为准，不新增前端依赖。

移除已完成文件卡片的内联打开入口，把「打开文件」「打开目录」放在「另存为」上方；菜单与更多入口共用可用性判断。打开目录应定位本地文件；使用现有受信任文件路径检查和平台命令。未接收、失效、已删除文件禁用相关操作。生产改动需通过桌面实际系统默认应用和文件管理器验收。

## 4. 实施验收用例

| 场景 | 验收结果 |
|---|---|
| A 有旧固定地址，B 从 IP1 切到 IP2 | 无须重新手填；自动或手动刷新后验证 IP2 并更新所有界面，记录不重复 |
| 旧 IP 被设备 C 占用 | 身份核对失败，不向 C 发送正文，不把 C 合并为 B |
| NAT 映射端口与 UDP 观察端口不同 | 已验证可用的固定端点仍可用，不机械覆盖端口 |
| Wi-Fi / 有线 / VPN 多候选 | 选择验证成功的候选；失败/迟到结果不覆盖较新验证结果 |
| 对方广播可见但消息端口关闭 | 显示已发现但连接不可用，不虚报送达 |
| 消息写出后对方落库失败 | 不进入已送达；有协商能力时显示明确拒收，否则未确认 |
| 消息已保存但回执丢失 | 同一消息 ID 重试，对方只保留一条，重新回执后最终送达 |
| 仅 A 能主动连接 B | 首发和补发均能通过同连接获得回执 |
| 发出后进程重启/休眠 | 待确认队列恢复；已读消息不退回等待状态 |
| 离线发送引用/公告/群聊 | 相应收件人恢复后补发，类型和提及信息保持一致 |
| 慢设备有大量待发消息 | 不阻塞其他设备投递和离线通知 |
| 收到文件右键操作 | 顺序正确；打开默认应用、目录定位、另存为各自可用；无内联打开按钮 |

回归需使用两个隔离实例及临时数据库、不同监听端口，覆盖 desktop 和 web；另安排真实 Windows 双机、DHCP 地址切换及反向不可达场景。记录设备 ID、候选来源/地址、选择原因、验证时间、连接耗时、消息 ID、尝试次数、回执耗时和错误类别；常规诊断日志不记录聊天正文。
