# XChat 稳定性与性能阶段二：实施与验收

日期：2026-10-09。对应[飞秋借鉴建议](feiq-inspired-stability-performance-recommendations.md)阶段二，起点为 `de5e87a`、版本 0.1.13。沿用共享 Rust 核心、现有界面和协议；没有增加第三阶段的远程控制功能。

本轮借鉴的是资源有界、任务持久化、故障隔离与恢复的设计原则。实现依据是 XChat 自身代码和测试，不将飞秋未恢复的算法当作已知事实。进度和知识交接见[阶段二计划](plans/2026-10-09-stability-phase-2.md)、根目录 `task_plan.md`、`findings.md`、`progress.md`。

## 已实现的行为

| 改造 | 当前行为 | 提交 |
| --- | --- | --- |
| 设备资源预算 | 所有存量传输共享发送预算；修改 4/8/16 配置不会叠加独立许可池。降档等待已有请求完成，超出新上限时不新增请求。 | `28f28fd` |
| 分块与完成重试 | 瞬时错误最多尝试 3 次；先查询原传输缺块，已提交的块直接确认，避免响应丢失后重复累计进度。 | `6e53694` |
| 进度落盘 | 同一接收任务的全部块共享 500 ms 常规持久化窗口；提交、回滚和终态立即写入。发送进度统计接收确认字节，无新确认不反复写 SQL。 | `6e53694` |
| 工作区同步 | 增量接口只返回有变化的集合；支持删除、进程/数据库更换、游标失效和定期全量校正。前端合并刷新请求，初始查询消除会话/传输 N+1。 | `9f318df` |
| 到期调度 | 按索引挑选到期投递、回执、撤回和可恢复文件，限量创建 worker；为前台消息留容量。 | `d03c560` |
| 接收背压 | 接收方声明可选并发能力，新发送端共享该对端上限；旧客户端多余请求在读 body 前有界等待。 | `13a970e` |
| 收尾边界修复 | 配置读取/保存与预算应用串行，防止旧值覆盖新值；文件控制响应限 64 KiB，含 chunked 响应。 | `9bb49ca` |

## 资源、重试与兼容契约

| 资源 | 有效上限 / 行为 |
| --- | --- |
| 全设备发送流 | 配置 4/8/16；不同配置世代共用同一预算。配置更新立即约束新增请求，旧任务分块布局保持不变。 |
| 单对端发送流 | `max(4, 全局上限 / 2)`，再取接收方声明上限的较小值。当前新接收端声明 4；选择 16 表示设备总容量，不承诺向单台设备开 16 流。 |
| 接收流 | 全局 8、每对端 4；最多 32 个取得许可前的请求，等待不超过 300 秒。旧 multipart 入口尚无对端 ID，只应用全局上限。 |
| 摘要 / 合并 | 分别最多 2 / 1；阻塞 I/O 放到阻塞线程，线程内实际工作完成前不释放许可。 |
| 磁盘 | 写块/合并前按挂载卷预留本次所需空间，保留 64 MiB 余量。预留覆盖在途块和合并副本，不是整个任务的容量承诺；外部占用或写失败仍回滚。 |
| 文本与控制 | 正文发送总槽位 4，后台最多 3，给前台留下容量；ACK/撤回另有 4 槽，不占文件许可。 |
| 补发 / 维护 | 每次最多挑选 32 个到期对端；补发 worker 最多 16、每对端每轮 1 条正文。后台连接检查最多 8 worker，30 秒一轮最多维护 16 个在线对端。 |

等待队列跳过已占满本对端配额的请求，使其他设备仍能取得空闲流。接收预算独立于发送预算，避免同一进程双向传输互等。大量在线设备的完整维护周期会随批次数增加；发现和用户主动发送仍即时验证连接。

块级重试只接受连接/超时及 HTTP 408、429、502、503、504，间隔 250/500 ms；身份、冲突、格式、存储等永久错误不循环重试。连接超时 5 秒，无数据进展 30 秒，发送完等待接收处理 300 秒，单块总预算 1 小时；取消会终止许可等待、网络请求或退避。控制响应超过 64 KiB 永久失败，避免异常对端造成无限内存增长。

保留 v1–v4 的任务身份、分块布局、旧端回退、续传、租约和幂等规则。`max_parallel_channels` 是 prepare 的可选响应字段：旧服务端缺省可读、旧客户端忽略。本轮没有贸然改写连接复用或接收布局。

数据库采用增量建表、列和索引，启动补全旧待发送任务；receipt 插入与投递记录创建同事务。内部新增 `ack_peer_id` 区分真正待回送的入站 ACK，保留既有回执标记含义。撤回会取消尚未送达的投递并撤销租约。

## 工作区同步规则

- 新增 HTTP `GET /api/workspace/sync?cursor=...` 和 Tauri `sync_workspace`，两者共用 Rust 实现；旧 `/api/workspace` 保留。
- SQLite 触发器按会话、设备、文件、传输、设置记录版本。相同值更新和只续租而无可见变化的更新不触发集合刷新。
- 游标包含进程、数据库身份和集合版本；先采集版本再读集合，期间发生的变更会在下次补回。错误/跨实例/过期游标或设置变化返回完整基线；最长 30 秒校正一次。
- 集合变化后整体替换，空数组表示删除完成，不保留幽灵记录。前端最多一个在途请求和一轮合并后续刷新，避免队列堆积及读取变更前状态。
- 旧后端不支持增量时回退到原接口；短暂网络故障保留游标并上报错误。历史 `conversation_id=NULL` 消息保留原迁移读取路径。
- 文件中心继续核验可信文件元数据；大历史文件集合的首次读取/全量校正仍有成本，不把空增量耗时当作全部页面的耗时。

## 本机测量

空闲工作区使用同一 Windows 主机、debug 构建、300 个离线联系人、100 条历史文件、20 个有效样本，关闭发现并使用临时数据库。两次预热不计入样本；原接口全量轮询与新接口空闲增量轮询分别代表改造前后的日常请求方式。

| 指标 | 改造前 | 最终复测 |
| --- | --- | --- |
| 平均响应 | 1449.313 ms | 14.632 ms |
| P95 | 1897.395 ms | 25.636 ms |
| 平均响应体 | 400761 bytes | 253 bytes |

原始记录：[基线](verification/2026-10-09-phase2-baseline.json)、[最终工作区](verification/2026-10-09-phase2-workspace.json)。最终脚本另记录首次基线 240.794 ms / 401011 bytes、一次旧全量接口 180.651 ms / 400761 bytes；这两项各只有一个样本。空闲增量成本降低不代表首次打开或每 30 秒校正也只需 14.632 ms。最终采样时没有本轮构建任务并行运行。

文件混合负载使用两个独立 Rust headless 进程、已验证固定地址、临时数据库与下载目录。合成发送器以有界缓冲发 v4 文件，接收、磁盘、合并、摘要、发布和文本/ACK 全部走真实 Rust 服务。文件计时含上传和最终确认，不含夹具准备及事后独立摘要复核。

| release 文件场景 | 块数 | 上传 / 最终确认 | 最终可用总耗时 | 本机吞吐 |
| --- | --- | --- | --- | --- |
| 0 B，4 请求并发 | 1 | 0.189 / 0.102 s | 0.290 s | — |
| 1 KiB，4 请求并发 | 1 | 0.130 / 0.150 s | 0.280 s | — |
| 64 MiB，4 请求并发 | 16 | 1.073 / 0.556 s | 1.629 s | 39.29 MiB/s |

| 4 GiB + 1 B，16 请求并发 | 1025 | 119.078 / 33.210 s | 152.289 s | 26.90 MiB/s |

所有文件都通过大小/SHA-256/终态核对和重复完成确认，小文件另验证重复块。release 整轮 1352 条文本均收到持久 ACK：平均 81.857 ms、P95 154.673 ms、最大 1413.036 ms；接收峰值工作集 34.33 MiB，发送进程 27.43 MiB，两个服务保持 ready/generation=1。4 GiB+1 场景接收进程消耗 215.953 CPU 秒、进程写 I/O 8,835,465,100 bytes；进程 I/O 包含网络，不能当作物理磁盘写入量。

原始数据：[release 大文件](verification/2026-10-09-phase2-load-release.json)、[debug 混合负载](verification/2026-10-09-phase2-load.json)。debug 的五个小文件场景也全部通过，199 条 ACK 无失败，P95 230.499 ms，接收峰值工作集 37.90 MiB。

这些是本机回环、合成文件发送器的结果；大文件测试期间还有本轮 Rust 编译负载。不同并发场景的分块数量也不同，不能据此归因“通道越多一定更快/更慢”。没有改造前同条件文件吞吐基线，不宣称文件吞吐提升倍数；没有把它当作 Rust 原生发送端、真实 SSD 极限、慢盘或 Wi-Fi 的性能。

## T6–T9 验收与限制

| 场景 | 已执行的证据 | 尚未执行的部分 |
| --- | --- | --- |
| T6 混合负载 | 双进程文件+真实文本/ACK；多世代、跨任务/对端公平性及许可取消测试；接收限额/旧客户端等待测试。 | 多台物理设备同时发送、真实网络拥塞；混合脚本未同时连续发取消请求，取消由专项故障测试覆盖。 |
| T7 故障与幂等 | 真实 HTTP 忙后恢复、持续忙最多 3 次、已提交但响应丢失、永久冲突、退避中取消；既有断流、源内容变化、磁盘/发布失败回滚、校验、同名文件和进程恢复回归。新增超大控制响应与配置竞态测试。 | 未填满实体磁盘或断开物理网卡；空间边界和错误路径通过受控注入验证。 |
| T8 大小与资源 | 0 B、1 KiB、64 MiB × 4/8/16、1 GiB、4 GiB+1；SHA-256、耗时、CPU、进程工作集和 I/O 记录。 | 未跑每一种大小与所有并发/硬件的笛卡尔积；慢盘、Wi-Fi、Android 实机仍需后续验收。 |
| T9 积压与同步 | 3000 离线联系人到期查询测试：无任务不产生补发、退避/租约排除、轮转和索引计划；300/100 工作区前后测量；Web/Tauri 实际页面新增/删除和空增量。 | 数万条文件首次全量读取、长时间多页面切换和跨机离线积压实测未覆盖。 |

4000 次模拟进度报告只取得 3 个常规写入窗口，提交/回滚仍强制持久化。该结果验证合并机制，不等价于磁盘吞吐提升倍数。集成过程中修复了 16 通道发送与每对端 4 流接收之间的立即拒绝问题，避免正常排队耗尽短重试次数。

本轮不升级版本、不生成安装包、不推送。所有重要实现按里程碑提交；原有 `analysis/`、安装版进程及日常聊天数据库保持原状。macOS/Linux/iOS 构建和 Android 实机未在本机验证。阶段三的新诊断/任务界面和远程协助另按批准计划及 UI 原型门禁推进。
